# 4 Tickets live in GitHub Issues, plans and traces stay in the repo

## Outcome
I want a project that opts in to keep its tickets in GitHub Issues so that a collaborator can
read, comment on and pick up work from the Issues tab, while the plan gate, briefs and traces
stay files, every skill, hook and script keeps working through one read-only mirror, and a
project that does not opt in keeps file tickets exactly as today.

## Acceptance criteria
- AC-0 (critical): Given a project without `kanban/.issues`, When any skill, hook, script or `make` target runs, Then tickets are files under `kanban/tickets/` as today: no `gh` call is made, the guard, lint rule 1 and every existing test behave unchanged.
- AC-1 (behavioral): Given a project whose `kanban/.issues` names `owner/repo` and whose Issues hold one issue labelled `ticket` and `ready` whose body has the ticket shape (frontmatter `id`, `parent`, `depends_on`, `writes`; sections Outcome, Acceptance criteria, Out of scope), When `make sync` runs, Then `kanban/tickets/<number>.<slug>.md` exists with `id: <number>`, `status: ready` taken from the label, the body sections verbatim, and every issue comment appended under `## Log` in creation order.
- AC-2 (property): For all issues the harness creates or edits, the body never contains a `status:` line; the label is the status, and `lint_kanban.py` fails on a mirrored ticket whose source body carries one.
- AC-3 (critical): Given `kanban/.active` names a mirrored ticket, When a Write or Edit targets a file under `kanban/tickets/`, Then the guard blocks it with a message naming `make sync`, while a write inside the ticket's `writes:` still passes and a write outside it is still blocked.
- AC-4 (behavioral): Given a ticket in `in_progress`, When `kanban_ops.py log <id> build "<head>" ["- line" ...]` runs, Then exactly one issue comment is created whose first line is `### [build] <YYYY-MM-DD HH:MM> — <head>`, and the mirror's `## Log` ends with that entry.
- AC-5 (behavioral): Given a ticket carrying one status label, When `kanban_ops.py status <id> <status>` runs, Then the issue carries exactly the new status label and no other status label; `done` and `superseded` also close the issue; `ready`, `in_progress` and `in_review` leave it open.
- AC-6 (critical): Given an issue that is closed, When any harness command would change its status, its body, or reopen it, Then the command refuses with a message naming the issue and makes no write call to GitHub; a human reopens from the Issues tab.
- AC-7 (behavioral): Given an approved plan, When the grill creates its tickets, Then one issue per slice exists with labels `ticket` and `ready`, `parent: <n>` and `depends_on` in the body frontmatter, and the plan's `## Slices` lines cite `#<number>` after the issues exist.
- AC-8 (behavioral): Given a rejected verdict with finding F#, When `kanban_ops.py child <id> F#` runs, Then a new issue is created with `parent` equal to the parent ticket's plan and `depends_on: [<id>]`, the verdict finding carries `home: <new number>`, and the parent's Log comment names the child.
- AC-9 (behavioral): Given the runner walks a plan and waits at Gate 2, When the ticket's status label becomes `done`, Then the walk continues with the next ticket in `depends_on` order; the order is computed from the mirror's `parent` and `depends_on` fields.
- AC-10 (behavioral): Given a collaborator commented on the ticket's issue, When the next `/gates:build <id>` session starts, Then the sync runs before the ticket is read and the comment is present in the mirror's `## Log`; the build skill names the sync step and a test pins the sentence.
- AC-11 (behavioral): Given the board renders, Then tickets are grouped under the plan named by their `parent:` field, the progress line counts slices by `#<number>`, and the dependency graph resolves `depends_on` issue numbers.
- AC-12 (behavioral): Given a closed issue whose body was edited after it closed, or which carries a `reopened` timeline event, When `lint_kanban.py` runs with GitHub access, Then it reports the issue number and what changed; without GitHub access it prints that the rule was not checked.
- AC-13 (behavioral): Given `init --issues <owner/repo>` on a project, When `gh auth status` succeeds and the repo has issues enabled, Then `kanban/.issues` is written, the `ticket` and five status labels exist, `kanban/tickets/` is git-ignored and `make sync` runs once; otherwise it refuses naming what is missing and writes nothing. Given the plugin's `Dockerfile`, Then it installs `gh`; Given the template's `.env.example`, Then it names `GH_TOKEN` with a comment on its scope; Given the template CI workflow, Then it runs the sync before `make kanban` and declares `permissions: issues: read`.
- AC-14 (behavioral): Given a project whose `kanban/tickets/` holds file tickets, When `init --issues` runs (`migrate_tickets.py` is its migration step), Then one issue per file is created with the same body shape, `done` and `superseded` ones are created closed, every Log entry becomes one comment in order, the plans' `## Slices` lines cite the new numbers, and the ticket files are deleted in one commit whose message lists old id → new number.
- AC-15 (human): Given the repo's Issues tab, a person confirms the tickets show their status labels, opens one, reads it as a ticket, and leaves a comment.
- AC-16 (human): Given a `ready` issue, a person confirms they can pick it up by creating the `ticket/<number>` branch and that the next build session on it shows their comment in the Log without anyone copying it.

## Out of scope
- GitHub Projects: the board renders from the mirror; Projects is optional and untouched.
- Issues without the `ticket` label (a collaborator's bug report) are not tickets and are never synced.
- A GitHub Action that flips a label when a branch is created; the label flips when the build starts.
- Editing a ticket's Outcome or ACs after creation, by any agent; a human edits on GitHub.
- The plan gate: `kanban/plans/<n>.plan.md` and its `approved:` line stay a file and a commit.
- Mixed mode inside one project: after opt-in every ticket is an issue; opting out is deleting `kanban/.issues` after a human migration, not a harness command.
- A ticket that exists in two editable places: the mirror is derived, git-ignored, and refused by the guard.
- Status kept in the issue body as text.

## Gate 1 notes
- Runtime dependency, opted-in projects only: `gh` on every machine that runs a skill, a hook or the runner (2.46.0 here; Debian package in the image). MIT-licensed. Projects without the marker need nothing new.
- Data leaving the repo: ticket text, Log entries, findings and verdict summaries go to the project's GitHub Issues; on a public repo they are public. This repo is public.
- Paid service: none; GitHub REST at 5000 requests per hour per login.
- Closed-issue immutability is a lint on GitHub's edit history, not a GitHub guarantee: anyone with write access can edit a closed issue's body from the web.
- Issues #2 and #3 on this repo are not tickets and stay untouched; ticket numbers start after them.

## Options
### Option 1 — the unattended runner writes issues from Docker
- (a) acquire: the human creates a fine-grained token with Issues read and write on the project repo and puts it in `.env` as `GH_TOKEN`; cost minutes, no delay, no AC changes.
- (b) substitute: run the runner locally under the stored `gh auth` login, verified working; Docker keeps `gh` installed (AC-13) and unattended runs wait for (a); no AC changes.
- (c) defer: drop the `.env.example` line from AC-13 to a later brief; nothing in this plan blocks.
- Recommend (b): no credential is copied anywhere for this plan, every AC is buildable now, and (a) stays the human's five minutes whenever a Docker run is wanted.
- Chosen: (b), 2026-09-14.

## Verdict must attack
- A ticket editable in two places: any code path other than the sync that writes under `kanban/tickets/`, or a commit that contains a mirror file.
- Status as body text: a writer that emits `status:` into an issue body, or a reader that trusts a body's status over the label.
- An agent path that reopens a closed issue or edits a closed issue's body: every `tickets.py` write must refuse on a closed issue before calling `gh`.
- The plan gate moved: any plan text, approval or slice list that lives on GitHub instead of `kanban/plans/`.

## Decisions worth an ADR
- Tickets as GitHub Issues with a derived, git-ignored mirror as the harness's read path.
- Issue numbers as ticket ids; children as ordinary issues with `depends_on`.
