# 4.1 Tracer bullet: the opt-in marker, and one issue synced into a read-only mirror and onto the board

## Outcome
A project with `kanban/.issues` runs `make sync` and one labelled issue appears as `kanban/tickets/<number>.<slug>.md`, on the board under its plan; a project without the marker is untouched.

## Acceptance criteria
- AC-1 (critical): Given no `kanban/.issues`, When any script, hook or `make` target runs, Then no `gh` call is made and every existing test passes unchanged (plan 4 AC-0)
- AC-2 (behavioral): Given `kanban/.issues` = `owner/repo` and one issue labelled `ticket` and `ready` with the ticket-shaped body, When `make sync` runs (`scripts/tickets.py sync`), Then `kanban/tickets/<number>.<slug>.md` exists with `id: <number>`, `status: ready` from the label, body sections verbatim, comments under `## Log` in order (plan 4 AC-1)
- AC-3 (property): For all issues the harness writes, the body has no `status:` line; a source body with one is reported by the sync (plan 4 AC-2)
- AC-4 (critical): Given the marker and `kanban/.active`, When a Write or Edit targets `kanban/tickets/`, Then the guard blocks with a message naming `make sync`; `writes:` scope still applies as today (plan 4 AC-3)
- AC-5 (behavioral): Given mirrored tickets with `parent:` and `#<number>` slices, When the board renders, Then tickets group under their plan and the progress line counts slices by number (plan 4 AC-11)
- AC-6 (behavioral): Given a repo whose labels lack the statuses, When the sync runs, Then `ticket` and the five status labels are created with `gh label create --force`

## Out of scope
- `kanban_ops` writes, skills, lint, migration — later slices
- GitHub Projects
