# 4.2 The write path: Log comments, status labels, closed-issue refusal, child issues; build and verdict skills write through kanban_ops

## Outcome
In an opted-in project every Log entry is an issue comment and every status is a label swap, all through `kanban_ops.py log|status|child`, with the mirror re-synced after each write; a closed issue refuses every write.

## Acceptance criteria
- AC-1 (behavioral): Given a ticket `in_progress`, When `kanban_ops.py log <id> build "<head>" ["- line"]` runs, Then one comment is created whose first line is `### [build] <YYYY-MM-DD HH:MM> — <head>` and the mirror's `## Log` ends with it (plan 4 AC-4)
- AC-2 (behavioral): Given one status label, When `kanban_ops.py status <id> <status>` runs, Then exactly the new status label remains; `done` and `superseded` close the issue, the other three leave it open (plan 4 AC-5)
- AC-3 (critical): Given a closed issue, When any `kanban_ops` or `tickets.py` command would change status, body or reopen it, Then it refuses naming the issue and makes no write call (plan 4 AC-6)
- AC-4 (behavioral): Given a rejected verdict finding F#, When `kanban_ops.py child <id> F#` runs, Then a new issue exists with the parent's `parent`, `depends_on: [#<id>]`, the finding carries `home: #<new>`, and the parent's Log comment names it (plan 4 AC-8)
- AC-5 (behavioral): Given the marker, When `ship`, `reject`, `waive`, `home` run, Then their Log entries and status changes go to the issue and no ticket file is committed; without the marker they behave as today (plan 4 AC-0)
- AC-6 (behavioral): Given the build and verdict skills, Then their status and Log steps name `kanban_ops.py log` and `kanban_ops.py status`, `kanban/.active` holds the issue number, and `reanchor.sh` finds the mirror file; a test pins the sentences
